01What src/ is

src/ is the entire application source: bootstrap, configuration, infrastructure clients, platform capabilities, business modules, shared HTTP plumbing, and the generated Prisma client. It is deliberately split into layers so that business rules stay independent from databases, brokers, and web frameworks.

The guiding idea: business code expresses what the ERP does (create a vendor, approve a purchase order, post an invoice). Platform code provides reusable capabilities (transactions, outbox, tenancy, numbering, messaging). Infrastructure code owns the actual third-party clients (Prisma, RabbitMQ, Kafka, Redis, S3). The dependency arrow always points from business toward platform, and from platform toward infrastructure. It never points back.

Why folders instead of one big file?

Each folder has a single responsibility. A reader can find the right place to change behavior without scanning the whole app, and an automated ESLint rule can enforce that the boundary is respected.

Why ports and adapters?

Business code depends on abstract ports such as OutboxWriterPort or VendorCommandRepository. Adapters bind those ports to Prisma, RabbitMQ, or an in-memory fake. This makes the domain testable and swappable.

Why so many platform folders?

The platform is a catalogue of capabilities that many business modules reuse. Keeping them separate avoids duplication and keeps cross-cutting concerns such as tenancy, audit, and retries in one place.

Why a modular monolith?

The application deploys as one Nest process, but each bounded context has clear internals and public contracts. That gives modular boundaries without the operational cost of microservices.

02Folder map at a glance

The top level of src/ is intentionally small. Everything else hangs off these entry points and layers.

src/ ├── main.ts # process entry point ├── app.module.ts # root Nest module: wires all layers + global providers ├── bootstrap/ # app composition: security, HTTP, Swagger, shutdown ├── config/ # typed environment configuration (only place reading process.env) ├── common/ # shared application types + HTTP plumbing (guards, filters, pipes) ├── infrastructure/ # third-party client creation (Prisma, Redis, brokers, S3, SES) ├── platform/ # reusable capabilities exposed as ports ├── business/ # ERP bounded contexts and domain logic └── generated/ # generated Prisma client (never edit by hand)
src/main.ts

Process entry point

Imports reflect-metadata and calls bootstrap(). It contains no application logic. The real composition lives in bootstrap/.

src/app.module.ts

Root module

Imports ConfigModule, ThrottlerModule, InfrastructureModule, PlatformModule, and BusinessModule. It registers global guards, pipes, interceptors, and the exception filter.

03Layer model and dependency direction

The architecture is a hexagonal / ports-and-adapters modular monolith. The dependency direction is enforced by ESLint, so a violation fails the build rather than living in a code review comment.

Business layer — src/business ERP use cases, aggregates, domain events, business policies. Depends only on platform ports and public contracts of other business modules.
depends on ports
Platform layer — src/platform Reusable capabilities: context/CLS, outbox, inbox, messaging, locking, idempotency, numbering, audit, notifications, scheduler, saga, tenancy, RBAC/ABAC.
wraps and configures
Infrastructure layer — src/infrastructure Raw client setup: Prisma read/write, Redis/Memcached, RabbitMQ, Kafka, SQS, BullMQ, S3, SES/SNS. No business rules.
reads typed settings from
Configuration — src/config Typed registerAs blocks and a ConfigService facade. This is the only folder allowed to read process.env.
used by all layers
Shared HTTP / application plumbing — src/common API response types, pagination, exceptions, tenant-scope helpers, guards, interceptors, validation pipe, RBAC decorator, middleware.

Dependency rule in one sentence: business may import platform ports; platform may import infrastructure; infrastructure and platform must never import business; domain folders must not import NestJS.

Layer May import Must not import
Business module Its own internals, platform ports, shared-business, another module's public/** or application/outbound-ports/** @infrastructure/**, another module's domain/application/infrastructure internals
Platform Infrastructure clients, config, shared-kernel/common primitives Any @business/** import
Infrastructure Third-party clients, config, common exceptions Business logic or ports
Domain Pure TypeScript, shared-business primitives, other domain objects NestJS, Prisma, broker clients, platform imports

04bootstrap/ — application composition

This folder is the composition root. It takes the Nest application and turns on every cross-cutting concern in the correct order: error tracking, HTTP server, CORS, security, request ID, Swagger, and graceful shutdown.

What happens at startup

1
configureSentry() Initializes error tracking before anything else can throw.
2
NestFactory.create(AppModule, FastifyAdapter) Creates the Nest application on Fastify with request/body/timeouts and log buffering.
3
Company config middleware Reads x-company-id, resolves company settings, and stamps them into CLS before route handlers run.
4
Composition-root bridges configureBatchOperations, configureImports, configureNotifications, and configureWebhooks register business handlers with platform registries.
5
Security, CORS, HTTP, shutdown, Swagger Helmet, CORS allow-list, /api prefix and URI versioning, shutdown hooks, and Swagger UI at /api/docs.
6
configureServer() Binds the listener on PORT (default 4000) and logs the final URL.

Why composition is separate from modules: some platform features need business handlers that cannot be imported by the platform layer. The bootstrap layer is the one place allowed to know both sides, so it bridges them without creating a business-to-platform dependency cycle.

05config/ — typed configuration

Configuration is a first-class layer. It is the only place that touches process.env, and it exposes a typed facade so the rest of the app never reads raw environment strings.

config/*.config.ts

One file per concern

App, database, cache, messaging, storage, security, outbox, scheduler, import, notification, observability, webhook, saga, idempotency. Each exports a registerAs() block with defaults.

config/config.module.ts

Global config module

Loads every registerAs block through Nest ConfigModule.forFeature and exports the typed ConfigService.

config/config.service.ts

Typed facade

Adapters call getPostgres(), getRabbitMQ(), getOutbox(), getSecurity(), and so on. Defaults live here, so missing env vars do not crash unrelated features.

.env.example

Environment contract

Documents every supported variable: database URLs, Redis, RabbitMQ, Kafka, SQS, S3, SMTP/SNS, JWT secrets, tenancy mode, outbox cadence, and worker tuning.

06infrastructure/ — third-party clients

This layer owns connections and SDK initialization only. It does not contain use cases, domain rules, or business decisions. If business code needs a capability, infrastructure exposes a client, and platform wraps it in a port.

database/prisma

PostgreSQL access

PrismaWriteService for writes and PrismaReadService for reads/replicas. The CLS transactional plugin binds @Transactional() to the write client.

redis

Redis / Memcached

Connection setup for cache, distributed locks, and idempotency ledgers. Business code uses CachePort or DistributedLockPort, never a raw client.

messaging

RabbitMQ / Kafka / SQS

Broker configuration and consumer hosts. Outbox dispatch publishes through MessageQueuePort; listeners receive through subscribe decorators.

queue

BullMQ

Redis-backed job queues for schedulers, batch jobs, imports, and other background work. Workers are infrastructure adapters behind platform ports.

storage

S3 / MinIO

Object storage setup for file uploads, imports, and generated documents. Business code talks to FileStoragePort.

notification

SES / SNS

Email and push/SMS provider clients. Notification templates and delivery policy live in the platform; this folder only creates the provider clients.

context

CLS + transaction plugin

Initializes nestjs-cls globally and registers the Prisma transactional adapter, so @Transactional() works across use cases and repositories.

07platform/ — reusable capabilities

The platform is the reusable capability layer. Each capability exposes an abstract class as its DI token (a port), plus an adapter that implements it. Business modules import PlatformModule and depend on those ports.

Three platform families

platform/platform-common

Cross-cutting runtime

Context/CLS, outbox, inbox, events, messaging, idempotency, locking, numbering, audit, notification, cache, storage, scheduler, saga/process orchestration, recurring, batch operations, import, webhook, rate limiting, tenancy, tax, currency, and more.

platform/platform-organization

Organization model and access

Company configuration, RBAC/ABAC authorization, organization, branch, plant, warehouse, department, entitlements, localization, custom fields, workflow, rules, automation, reporting, dashboard, global search, and SDUI metadata.

platform/platform-ai

AI-facing capabilities

Chat, model registry, MCP integration, and an AI gateway. These are ports and adapters that business modules can consume without owning provider SDKs.

What a platform capability looks like

platform/platform-common/outbox/
├── ports/
│   ├── outbox-writer.port.ts        # public port business code injects
│   └── generic-outbox-publisher.port.ts
├── adapters/
│   └── shared-outbox.adapter.ts     # reusable adapter used by every module
├── services/
│   └── outbox.service.ts            # implements OutboxWriterPort
├── usecases/
│   ├── append-outbox-event.usecase.ts
│   └── publish-pending-batch.usecase.ts
├── repositories/
│   └── prisma-outbox.repository.ts  # SQL / outbox_messages table
├── outbox.scheduler.ts              # periodic dispatch tick
└── outbox.module.ts                 # bindings and exports

Why this matters: business modules never import Prisma, amqplib, kafkajs, ioredis, or a provider SDK. They import a port. That keeps domain code testable, lets adapters be replaced, and stops infrastructure details from leaking into business rules.

Key ports you will see often

Port What it gives business code
RequestContextPortCurrent tenant, company, user, roles, locale, request/correlation IDs from CLS.
OutboxWriterPortAppend an event inside the current database transaction.
MessageQueuePortPublish an outbox envelope to RabbitMQ, Kafka, or SQS.
InboxPortDeduplicate and track inbound messages so retries are idempotent.

08business/ — the ERP itself

This is where the actual ERP behavior lives. Each bounded context is a Nest module with a domain model, application use cases, persistence adapters, HTTP presentation, and a public contract for other modules.

Bounded contexts in this project

party/vendor

Vendor master data

Create, update, activate, deactivate, block, and look up vendors. Natural key is code, unique per company.

product-management/product

Product master data

Products, SKUs, pricing fields, status transitions, and purchasable-product lookups. Natural key is sku.

product-management/product-pricing

Price lists

Price-list creation, line management, activation, archiving, and price resolution for sales/purchasing.

procurement/purchase-order

Purchase orders

Draft-to-closed lifecycle, approval, issue, amendment, receipts, recurring generation, and optimistic concurrency on version.

procurement/purchase-goods-receipt

Goods receipt notes

Receive against a PO, track received quantities, post, reverse, and emit stock-movement events.

sales/invoice

Sales invoices

Invoice creation, posting, recurring generation, and invoice-for-reports facade.

shared-business

Framework-free domain primitives

Entity, aggregate root, value object, domain event bases, plus money and quantity value objects. No NestJS, no Prisma, no platform imports.

Why these contexts are separate

  • Vendor owns vendor identity and orderability.
  • Product owns product identity, SKU, and price master data.
  • Purchase Order owns ordering intent and approval state.
  • GRN owns receipt evidence and received quantities.
  • Inventory owns stock movements and balances.
  • Finance owns accounting entries and payment state.
  • Invoice owns sales invoicing and recurring sales documents.

Cross-context reads go through public ports or facades. For example, Purchase Order does not import Vendor internals; it calls a vendor query port exposed by the vendor module.

09common/ — shared application and HTTP plumbing

common/ is not business logic. It contains small, reusable technical pieces that every layer can rely on: response envelopes, pagination, exceptions, tenant helpers, guards, interceptors, pipes, decorators, and middleware.

common/application/types

Shared contracts

ApiResponse, PageQuery/PageResult, device context, JSON value types, and wire-date types.

common/application/utils

Cross-cutting helpers

TenantScope builds tenant predicates and throws 404 for foreign rows; env helpers, failure messages, chunking, and Prisma JSON helpers.

common/application/exceptions

Error taxonomy

Domain and infrastructure exception bases map cleanly to HTTP responses without leaking stack traces or SQL details.

common/http/guards

Request gating

Throttler guard, RBAC guard (reads @Rbac(resource, action)), and the platform tenancy/auth guard.

common/http/interceptors

Request/response shaping

Request ID and correlation ID seeding, logging, success envelope wrapping, and device-specific response mapping.

common/http/pipes

Validation

AppValidationPipe is a Zod validation pipe, so request DTOs can be schemas rather than class-validator decorators.

common/http/decorators

Metadata markers

@Rbac(), @DeviceResponse(), @SkipTenancy(), device-context decorator, and Kafka event decorator.

common/http/middleware

Pre-route context

CompanyConfigContextMiddleware resolves company configuration before route handlers and stamps it into CLS.

10generated/ — generated Prisma client

This folder is generated by Prisma from prisma/schema/. It is not hand-written application code.

Never edit src/generated/**. Run npx prisma generate after schema changes. The Prisma schema is split by context under prisma/schema/<context>/; there are no migration files in this project. Use npm run db:push to sync the database from the schema.

11Anatomy of a business module

Every aggregate module follows the same shape. This is the pattern to copy when adding a new business capability.

business/<context>/<module>/ ├── domain/ # pure business rules, no framework imports │ ├── aggregates/ # aggregate root + invariants │ ├── entities/ # child entities owned by the aggregate │ ├── value-objects/ # typed IDs, codes, quantities, money │ ├── events/ # domain events raised by the aggregate │ ├── policies/ # reusable decision rules │ ├── factories/ # create/reconstitute aggregates │ ├── repositories/ # abstract command repository port │ └── types/ # domain types and enums ├── application/ │ ├── use-cases/ # one use case per file, orchestrates domain + ports │ ├── queries/ # abstract query port │ ├── facades/ # cross-module read/orchestration contracts │ ├── outbound-ports/ # ports this module needs from others │ └── publishes/ # event publisher ports (when present) ├── infrastructure/ │ ├── persistence/prisma/ # Prisma repositories + mappers │ └── adapters/ # platform / other-module adapters ├── presentation/http/ │ ├── <module>.controller.ts # thin HTTP layer │ ├── requests/ # Zod request DTOs │ └── responses/ # web/mobile response DTOs ├── public/ # the only folder other modules may import │ ├── contracts/ │ └── ports/ ├── integrations/ # event listeners (when present) │ └── consumes/listeners/ ├── specifications/ # side-effecting integration tests │ └── application/use-cases/ └── <module>.module.ts # bindings/exports only

Folder-by-folder responsibilities

Folder Used for Why it exists
domain/ Aggregates, invariants, value objects, events, policies, factories, repository ports. Keeps business rules pure, testable, and independent of Nest, Prisma, and brokers.
application/ Use cases, queries, facades, outbound ports, publisher ports. Orchestrates domain objects and ports. This is the transaction and authorization boundary.
infrastructure/ Prisma repositories, mappers, and adapters that bind ports to real clients. Isolates persistence and third-party details so domain and application stay clean.
presentation/http/ Controllers, request DTOs, response DTOs. Thin transport layer. Controllers validate shape and call use cases; they contain no business rules.
public/ Contracts and ports other business modules may consume. Creates a deliberate cross-module contract instead of allowing deep imports into internals.
integrations/ Message listeners that delegate to use cases/facades. Connects external events to business behavior without putting broker logic in the domain.
specifications/ Integration tests that exercise Prisma, outbox, messaging, or Nest bootstrap. Separates side-effecting tests from fast co-located unit specs.
<module>.module.ts Providers, port bindings, controllers, exports. Keeps wiring visible in one place and prevents hidden global state.

Command use case contract

@Injectable()
export class CreateVendorUseCase {
  constructor(
    private readonly repo: VendorCommandRepository,
    private readonly events: VendorPublisherPort,
    private readonly ctx: RequestContextPort,
    private readonly abac: AbacPort,
  ) {}

  @Transactional()
  async execute(input: CreateVendorRequest): Promise<string> {
    const context = this.ctx.require();          // 1. tenant/company/user from CLS
    const decision = await this.abac.evaluate(...); // 2. authorize before business steps

    const vendor = VendorFactory.create(input);  // 3. factory -> aggregate
    await this.repo.save(vendor);                // 4. repository port -> Prisma in transaction

    for (const event of vendor.pullEvents()) {   // 5. outbox in same transaction
      await this.events.send(event, vendor.id.toString());
    }
    return vendor.id.toString();
  }
}

12Request lifecycle flow chart

This is what happens from the moment an HTTP request arrives to the moment a response is returned. The same flow applies to every business endpoint, whether it is a vendor, product, purchase order, GRN, or invoice.

1
Client → Fastify listener main.ts starts bootstrap(); the app listens on PORT (default 4000). All routes are under /api/v1 because of the global prefix and URI versioning.
2
Company config middleware Reads x-company-id, loads company settings through CompanyConfigPort, and stamps defaultCurrency, autoApproveThreshold, and overReceiptTolerance into CLS.
3
Global guards Throttler checks rate limits. TenancyAuthGuard enforces the tenancy mode (trusted headers in single, JWT with tenantId in multi). RbacGuard reads @Rbac() metadata and calls RbacPort.can().
4
Request ID interceptor Generates requestId, reuses incoming x-correlation-id, and seeds the CLS RequestContext with tenant, company, user, roles, locale, IP, and user agent.
5
Zod validation pipe AppValidationPipe validates the request DTO. Invalid input never reaches a use case.
6
Thin controller The controller reads params/body/query, calls exactly one use case, and returns an ApiResponse envelope. It contains no business logic.
7
Use case: context + ABAC Reads RequestContextPort, then calls AbacPort.evaluate() before any business step. A DENY becomes ForbiddenException.
8
Domain: factory → aggregate → invariants The factory creates or reconstitutes an aggregate. Value objects and invariants enforce rules such as unique-in-company codes, valid status transitions, non-negative quantities, and approval limits.
9
Repository port → Prisma adapter The use case calls an abstract repository port. The Prisma adapter writes through TransactionHost using the CLS transaction. Reads apply TenantScope; a foreign row returns 404, never 403.
10
Domain events → outbox (same transaction) The aggregate raises events. The use case drains pullEvents() and calls a publisher port, which binds to SharedOutboxAdapter → OutboxWriterPort. The event row commits atomically with the aggregate.
11
Transaction commits If anything throws, the transaction rolls back: no half-written aggregate and no orphan outbox row.
12
Response shaping ResponseInterceptor wraps the result as { status, statusCode, data, message }. DeviceResponseInterceptor maps mobile or web DTOs based on x-device-type. HttpExceptionsFilter maps failures to a consistent error shape.

Why the order matters: company config must be in CLS before ABAC and numbering; request/correlation IDs must be set before repositories and outbox writes; validation must happen before the controller; ABAC must happen before business steps.

13Transactional outbox and event flow

The outbox solves the dual-write problem: a use case must update the database and publish an event without losing one if the other fails. The event is written in the same database transaction; a separate scheduler publishes it later.

1
Inside the business transaction UseCase.execute() is annotated @Transactional(). It saves the aggregate through a repository and appends events through OutboxWriterPort.
2
outbox_messages row is inserted AppendOutboxEventUseCase stores event ID, type, aggregate, payload, tenant/company, correlation/causation IDs, broker, and next retry time.
3
Commit The aggregate row and the outbox row commit together. Nothing has left the process yet.
4
OutboxScheduler tick Runs on OUTBOX_POLL_INTERVAL_MS (default 10 seconds). It calls PublishPendingBatchUseCase.
5
Claim due rows claimBatch() uses FOR UPDATE SKIP LOCKED plus a lease token, so multiple workers can run safely without double-publishing.
6
Publish to broker MessageQueuePort.publish(envelope) sends to RabbitMQ (topic exchange), Kafka (topic per event type), or SQS, depending on the envelope's broker header.
7
Also emit in-process The same envelope is emitted on InProcessEventBus inside a restored request context, so local listeners receive it without a broker round trip.
8
Mark published or retry On success the row is CAS-marked PUBLISHED. On failure it stays PENDING with exponential backoff. Exhausted rows become DEAD_LETTER.
RabbitMQ consumer

Listener subscribes to the topic exchange, validates the envelope, and delegates to a use case or facade. Duplicate delivery is handled by the inbox or natural idempotency keys.

Kafka consumer

Listener consumes the event-type topic, restores tenant/correlation context, and delegates to the same use case or facade.

In-process listener

Local event-emitter listener receives the same envelope immediately, useful for same-process reactions such as projections or notifications.

Delivery guarantee: at least once. The outbox row is only settled after publish succeeds. Consumers must be idempotent; the inbox table and unique natural keys are the mechanisms that make redelivery safe.

14Rules that keep the architecture clean

These are not suggestions. They are enforced by ESLint and by the module structure, and they are the reason the codebase stays navigable as it grows.

1. Business talks to ports only

No @infrastructure/** imports in business modules. No raw Prisma, amqplib, kafkajs, ioredis, or provider SDKs. If you need a capability, inject a port from PlatformModule.

2. Platform never imports business

Platform defines its own contracts. Business handlers are bridged into platform registries from src/bootstrap/configure-*.ts.

3. Domain is framework-free

Folders under domain/ and shared-business/domain/ must not import @nestjs/*, Prisma, or platform types.

4. One use case per file

Use cases are the transaction and authorization boundary. They read context from RequestContextPort, call AbacPort first, then orchestrate factory, aggregate, repository, and outbox.

5. Side effects leave through the outbox

Publishing, notifications, webhooks, and cross-context reactions are appended inside @Transactional(). Use cases never publish directly to a broker.

6. Tenancy is explicit

Business tables carry tenantId/companyId. Reads and writes apply TenantScope. A row owned by another tenant is treated as missing (404), never 403.

7. Natural keys are company-scoped

Vendor code, product sku, PO orderNumber, GRN number, and invoice number are unique within a company, not globally.

8. Public contracts are deliberate

Other modules may import only another module's public/** or application/outbound-ports/**. Deep imports into domain, application, or infrastructure are forbidden.

15Where to add new code

Use this table as a practical map. It answers the most common "where does this go?" questions without guessing.

I want to add... Put it here Notes
A new HTTP endpoint business/<context>/<module>/presentation/http/ Controller + request DTO + response DTO. Controller calls an existing use case; no business logic in the controller.
A new command use case application/use-cases/<verb>-<noun>.usecase.ts @Transactional(), RequestContextPort, AbacPort, factory, repository, outbox.
A new aggregate or entity domain/aggregates/ or domain/entities/ Add invariants, value objects, events, factory, and repository port alongside it.
A new persistence model prisma/schema/<context>/ Edit schema, run npm run db:push, then npx prisma generate. No migrations.
A new repository domain/repositories/ (port) + infrastructure/persistence/prisma/ (adapter) Bind the port in <module>.module.ts.
A new platform capability platform/platform-common/<name>/ Create ports/, adapter, service, and module; import/export it from PlatformModule.
A new broker or client infrastructure/<area>/ Client setup only. Wrap it in a platform port before business code can use it.
A new environment variable config/<area>.config.ts + config/config.service.ts + .env.example Keep defaults in the config block; expose a typed getter.
A new event listener integrations/consumes/listeners/ or application/integrations/ Listener validates the envelope and delegates to a use case or facade.
A new cross-module read public/ports/ and public/contracts/ Export the port from the owning module; import it from the consuming module.
A unit test Co-located <name>.spec.ts Mock ports; no DB, broker, cache, or Nest bootstrap.
An integration test specifications/**/*.integration-spec.ts Use real Prisma, outbox, messaging, or Nest bootstrap; run with npm run test:integration:business.
